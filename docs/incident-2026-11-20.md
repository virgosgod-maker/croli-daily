# 事故记录：一次 refresh token 重放如何吊销整条凭据链

**日期**：2026-11-20
**影响**：本机 Croli 桌面端登录失效，需要重新登录一次。
**结论**：这是本项目最重要的约束，`TokenStore` 的单写者设计就是为了防它。

## 发生了什么

排查"能否在 NAS 上 7×24 自动签到"时，需要确认 access_token 能否长期续期。
于是对真机 `~/Library/Application Support/Croli/auth.json` 做了 refresh 实验：

1. 备份 `auth.json`；
2. `POST https://clerk.croli.net/oauth/token` `grant_type=refresh_token` → **200**，
   返回新的 `access_token` + **新的 `refresh_token`**（旧的被轮换掉）；
3. 为了确认"旧的还能不能用"，又拿**旧** refresh_token 发了一次 → 
   `{"error":"invalid_grant","...":"The refresh token was already used."}`；
4. 从这一步起，**新旧 access_token 全部 401**：
   `/v1/account/balance`、`/v1/ops/home`、`/v1/ledger`、
   Clerk 的 `/oauth/userinfo` 全部拒绝。

## 根因

Clerk（Croli 的认证服务）对 refresh token 启用了**重放检测**：
refresh token 是一次性的、轮换的；一旦检测到某个已用过的 refresh token 被再次提交，
系统判定"这条令牌链已泄露"，于是**吊销整条链（token family）**，
包括刚换出来的那一对。

这不是 bug，是 OAuth 2.0 的标准安全机制（RFC 6819 §5.2.2.3 一类的建议）。

## 对本项目的直接影响

1. **不能把桌面端的 `auth.json` 拿到 NAS 上用。**
   两边是同一份 refresh token，谁先刷谁把对方踢掉；如果两边几乎同时刷，
   第二方提交的是已用过的 token，触发重放检测 → **两边一起死**。

2. **不能"出问题就重放一次试试"。** 任何重试逻辑都必须只在**刷新失败后停手**，
   绝不能用旧 refresh token 再试。所以 `src/auth.mjs` 里刷新失败直接抛错，
   没有任何自动重试。

3. **必须保证单写者。** `TokenStore` 用 `auth.json.lock` 做进程级互斥，
   原子写（`tmp` + `rename`）+ `0600`，保证任何时刻只有一处能刷新并落盘。

4. **掉登录无法自动恢复。** Croli 关闭了 Clerk 的设备码授权
   （`POST /oauth/device_authorization` → `does not have the device_code grant`），
   所以没有"无人值守重新登录"的正路。只能人工登录一次，再把 `auth.json` 同步过去。

## 恢复步骤（如果又踩到）

1. 打开 Croli 桌面端，重新登录；
2. 把新的 `auth.json` 复制到工具用的那份：
   ```bash
   cp "~/Library/Application Support/Croli/auth.json" ~/.config/croli-daily/auth.json
   chmod 600 ~/.config/croli-daily/auth.json
   ```
3. 如果 NAS 上也有一份，用 `node src/cli.mjs sync-auth <path>` 更新它。
